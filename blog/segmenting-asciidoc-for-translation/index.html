    Not Everything Needs an LLM¶

    There's a growing instinct in AI engineering to route every task through a language model. It's understandable — frontier models are remarkably capable, and the path from problem to prototype is often just a prompt. But capability isn't the right criterion for every stage of a pipeline. The right question is: does this task benefit from intelligence, or is it better served by an algorithm?

    Classifying markup is a good test case. Given a chunk of HTML, a model can tell you which parts are translatable prose and which are structural tags. But the classification is entirely deterministic — <div class="warning"> is always markup, href="/deadline" is always a URL. No ambiguity, no judgment, no context dependence. It's a pattern-matching problem with a known, finite set of rules.

    Delegating it to a model anyway has real costs:

    Noise. Markup is structural noise in any language task. Every <div>, every class="...", every {attribute-ref} competes for attention in your model's context window without contributing semantic value. Tags pollute translation context, dilute RAG embeddings, and leak into fine-tuning datasets. Stripping noise before the model sees it isn't just an optimization — it improves output quality.

    Inconsistency. A model might preserve a URL in one paragraph and translate it in the next. It might strip a <span> tag it deems irrelevant, or shift a closing tag to match target-language word order. Run the same document twice and you may get structurally different output. A rule-based classifier produces identical results every time — which matters for translation memory alignment, regression testing, and auditable pipelines.

    Silent failures. When a model misclassifies a tag, the result is silent corruption: a broken link, a mangled attribute, a missing placeholder. You discover it in QA, or in production. A rule-based engine either matches a pattern or it doesn't — failures are visible, debuggable, and fixable by editing a regex.

    Cost at scale. A 1 MB document sent to a frontier model for markup-aware processing costs dollars and takes minutes. The same document through a compiled regex pipeline takes 25 ms and costs nothing. At thousands of documents per day, the preprocessing stage alone can dominate your budget.

    The best AI pipelines don't use models for everything — they use models where intelligence is needed and algorithms where determinism is needed. For structured text, that means: classify deterministically, then let the model focus on language.

    texplitter is an open-source library built on this principle. It tokenizes structured text with customizable regex rules, builds a segment tree, and extracts classified segments — with everything labeled by semantic class. The core is written in Rust (25 ms on a 1 MB document) and exposed to Python via pyo3.

    In this article I'll explain the approach, then demonstrate it by segmenting AsciiDoc — a format with enough structural variety to stress-test any segmentation engine.

    The segmentation problem¶

    Consider what "content" means in a real document:

    <div class="warning">
  <p>You <strong>must</strong> update before
  <a href="/deadline">March 15th</a>.</p>
</div>

    Of the 130 characters in this fragment, only 39 are content: "You must update before March 15th." The rest — 70% of the input — is structural noise. Every token of it competes for attention in your model's context window, and none of it needs language understanding to classify.

    Different pipelines need different things from the same document, but all of them benefit from removing the noise first:

    • Translation: "You must update before March 15th." — translatable text with formatting context, but not the <div> wrapper, the class="warning" attribute, or the URL.
    • RAG embedding: just the prose, no tags — but you want the heading trail for chunk context.
    • Fine-tuning: the prose paragraphs, stripped clean, but with code blocks excluded.
    • Structured extraction: the code blocks themselves, with their surrounding prose for context.

    All of these require the same preprocessing step: classify every token before it reaches any model. Is it translatable prose? A structural boundary? A symbol that must be protected? An inline tag that wraps content?

    This means segmentation isn't just "strip the tags." It's:

    1. Classify every piece of text: is it translatable, structural, a symbol that must be protected, or a sentence boundary?
    2. Build structure: which tags wrap which content? Where do sentences begin and end?
    3. Extract: pull out the pieces you need, with enough context to reassemble later.
    4. Protect: replace inline tags and symbols with safe placeholders that downstream processing can't corrupt.
    5. Rebuild: after processing, put the structure back.

    And the rules for what counts as "content" change depending on the format. HTML tags look like <b>, AsciiDoc bold looks like *bold*, Markdown uses **bold**, and DITA has its own vocabulary. A segmentation engine that only understands HTML is useless for half your content.

    How texplitter solves it¶

    texplitter's approach is a five-stage pipeline:

    Input text
  → Tokenize (customizable regex rules)
  → Build segment tree (iterative, handles any depth)
  → Extract classified segments
  → Generate placeholders
  → Rebuild after processing

    The key insight is that tokenization rules are data, not code. Each format gets a JSON ruleset — an ordered list of regex patterns, each tagged with a token class (TRANSLATABLE, BREAK, SYMBOL, OPEN_TAG, etc.). The tokenizer compiles all rules into a single combined regex and scans the input in one pass. First match wins: the rule whose pattern matches at the earliest position in the text is used.

    This means adding support for a new format doesn't require changing any code. You create a JSON file with rules for your format's syntax, and the same engine handles everything else.

    The segment tree¶

    Once tokenized, the flat token stream is organized into a tree:

    • Single nodes wrap content in tag pairs (<p>...</p>)
    • Binary nodes split at sentence boundaries (.)
    • Translatable leaves hold the actual text

    The tree is built iteratively using explicit work stacks — no recursion. This matters because real-world documents can nest hundreds of levels deep (think deeply nested <div> structures or AsciiDoc include chains), and a recursive approach would overflow the stack.

    Placeholders and rebuild¶

    When you extract segments, inline tags become placeholders:

    Original Segment Placeholder
    Click <a href="...">here</a> Click %%1%%here%%2%% %%1%% = <a href="@a/href~0@">, %%2%% = </a>

    For translation, the model sees Click %%1%%here%%2%% and produces Haga clic %%1%%aquí%%2%%. The rebuild step knows that %%1%% is the opening <a> tag and puts it back — even if the model reordered the sentence. For RAG or fine-tuning, you can simply discard the placeholder segments and keep only the TRANSLATABLE class.

    Worked example: segmenting AsciiDoc¶

    To show this isn't just an HTML trick, let's segment AsciiDoc — a format with its own structural syntax that shares nothing with HTML. (The AsciiDoc ruleset shipped with texplitter is provided as a sample to illustrate custom ruleset creation; it has not been fully tested in production scenarios.)

    The input¶

    == Getting Started

Install the {product-name} by running:

NOTE: You *must* have `Python 3.9` or later.

See <<installation>> for platform-specific instructions.

    This fragment has five different kinds of non-translatable structure:

    Construct AsciiDoc syntax What it means
    Section title == Heading level 2 — structural, not content
    Attribute reference {product-name} Expands at build time — must not be translated
    Bold formatting *must* Markers must survive round-trip
    Monospace `Python 3.9` Backtick markers must be preserved
    Cross-reference <<installation>> Anchor ID — translating it breaks the link

    Note that NOTE: is not structural — the word "NOTE" is translatable (NOTA in Spanish, REMARQUE in French), while the : separator naturally acts as a sentence break.

    The ruleset¶

    texplitter ships with a built-in AsciiDoc ruleset. Here are the key rules that handle the constructs above:

    Section titles become BREAK tokens (sentence boundaries):

    {
    "type": "asciidoc_section_title",
    "class": "BREAK",
    "regex": "^={1,5}\\s+"
}

    Attribute references become SINGLE_TAG tokens (protected inline nodes — pushed and immediately popped from the tag stack, like a self-closing HTML tag):

    {
    "type": "asciidoc_attribute_ref",
    "class": "SINGLE_TAG",
    "regex": "\\s*\\{[a-zA-Z0-9_-]+\\}\\s*"
}

    Bold text uses paired OPEN_BRACKET / CLOSE_BRACKET tokens so the content between the markers stays translatable:

    {
    "type": "asciidoc_bold",
    "class": "OPEN_BRACKET",
    "regex": "\\s*\\*(?=\\S)"
},
{
    "type": "asciidoc_bold_close",
    "class": "CLOSE_BRACKET",
    "regex": "(?<=\\S)\\*(?=\\s|[.,;:!?\\)]|$)"
}

    The opening marker matches optional whitespace + * before a non-space character; the closing marker matches * after a non-space character, followed by whitespace, punctuation, or end-of-string. The word between the markers is classified as TRANSLATABLE by the normal word rules, and the segment tree wraps all three tokens into a single subtree — so the content is accessible while the markers are protected.

    Cross-references become SINGLE_TAG (same rationale — they are self-contained inline elements that must not be translated):

    {
    "type": "asciidoc_xref",
    "class": "SINGLE_TAG",
    "regex": "<<[^,>]+(,[^>]+)?>>"
}

    All of these rules sit before the generic word and punctuation rules (inherited from the default HTML/XML ruleset). Because first-match-wins is positional, the AsciiDoc-specific patterns fire before the generic ones can claim the text.

    The code¶

    from texplitter import Tokenizer, SegmentTree

tok = Tokenizer("asciidoc")

text = """== Getting Started

Install the {product-name} by running:

NOTE: You *must* have `Python 3.9` or later.

See <<installation>> for platform-specific instructions."""

tokens = tok.tokenize(text)
tree = SegmentTree(tokens)
segments = tree.tree.extract_segments()

for seg in segments:
    for key, value in seg.items():
        if value:
            print(f"  {key}: {value!r}")

    The output contains only classified text. The section title prefix, attribute reference, and cross-reference are all classified correctly and separated from the translatable content. Bold and monospace content appears as translatable text within its formatting context.

    Using segments in different pipelines¶

    Once you have the classified segments, the same tree feeds different use cases:

    # Translation: send translatable segments to an API
for seg in segments:
    for key, value in seg.items():
        if value and "TRANSLATABLE" in key:
            translated = translate(value, target_lang="es")

# RAG: embed only the prose, skip structural tokens
prose = [v for seg in segments for k, v in seg.items()
         if v and "TRANSLATABLE" in k]

# Fine-tuning: extract clean text for training data

    After translation, rebuild_from_segments() reinserts the processed text into the original tree, preserving all markup structure.

    Building your own rulesets¶

    The AsciiDoc ruleset is just one example. The same pattern works for any structured format:

    1. Start from the default ruleset — it already handles words, numbers, punctuation, and whitespace in 30+ languages (including CJK).
    2. Prepend format-specific rules — they must come first because of first-match-wins ordering.
    3. Choose the right token class for each construct:
    4. BREAK for structural boundaries (titles, paragraphs)
    5. SYMBOL for non-translatable inline elements (URLs, emails)
    6. SINGLE_TAG for protected inline constructs that should be treated as self-closing nodes (attribute references, cross-references, inline macros, entities, <br/>)
    7. OPEN_BRACKET / CLOSE_BRACKET for paired formatting markers (keeps content between them translatable)
    8. BREAK_TEMPLATE for non-translatable blocks (code listings, directives)
    9. Test and iterate — texplitter ships with a browser-based config editor (texplitter config) for visually editing and testing rules.

    Performance¶

    The Rust core matters when you're processing real volumes. On a single 1 MB HTML file (~200,000 words):

    Approach Time Cost Deterministic
    texplitter (Rust) ~25 ms $0 Yes
    Pure Python regex ~8 min $0 Yes
    Frontier LLM minutes $2–10+ No

    The 20,000x speedup over pure Python comes from Rust's fancy-regex engine and iterative tree construction — no GIL contention, no Python object allocation per token.

    But speed isn't the only advantage over delegating to a model. The classification is deterministic: process the same document a thousand times, get the same segments every time. There's no temperature setting, no prompt sensitivity, no variation between Tuesday and Wednesday. For pipelines that need reproducible output — translation memory alignment, regression testing, auditable data extraction — this matters more than speed.
